# Requirements Document

## Project Description (Input)
Neo4jベースの障害者支援ネットワーク可視化システム

## Introduction

コミュニティ・リソース・グラフは、障害者・精神障害者の支援に携わる支援者、本人、家族が地域資源を共有・検索できるグラフデータベースシステムです。「完璧な地図」ではなく「生きた地図」として、使いながら情報が自然に成長していく「つながりの連鎖」方式を採用します。

Neo4jグラフデータベースをコアとし、資源(Resource)、タグ(Tag)、ユーザー(User)、フィードバック(Feedback)、ニーズ(Need)、エリア(Area)の6種類のノードと、それらの関係性を表すリレーションシップで構成されます。

### 主要なステークホルダー
- **相談支援専門員**: 利用者のニーズに合った資源を検索し、実際の使用経験を共有
- **本人・家族**: 実際に使っている場所の情報提供と当事者視点の評価
- **地域住民**: 障害理解のある場所・人の情報提供

### 成長設計
- Phase 1 (Week 1-4): 初期データ50-100件
- Phase 2 (Week 4-12): フィードバック蓄積とつながり情報の形成
- Phase 3 (Week 12-24): 地域の「生きた資源マップ」完成

## Requirements

### Requirement 1: 資源の登録管理
**Objective:** 支援者・本人・家族・地域住民として、知っている地域資源を登録し、コミュニティで共有可能にしたい。それにより、地域の支援資源が可視化され、誰もがアクセスできる情報基盤を構築できる。

#### Acceptance Criteria
1. When ユーザーが資源登録フォームを送信するとき、the システムは Resource ノードを作成し、必須プロパティ (id, name, type, created_at) を保存すること
2. When 資源タイプを選択するとき、the システムは place, person, activity, information の4つから選択可能にすること
3. The システムは resource.id を `{type}_{sequential}` 形式で自動生成すること (例: res_001, res_042)
4. The システムは created_at, updated_at を ISO 8601 形式で記録すること
5. When 資源を登録するとき、the システムは REGISTERED_BY リレーションシップで登録ユーザーと紐付けること
6. The システムは name, description, address, contact, hours などの詳細情報を任意フィールドとして保存できること
7. When 資源が登録されたとき、the システムは view_count と feedback_count を 0 で初期化すること

### Requirement 2: タグベース分類
**Objective:** 支援者として、資源を柔軟に分類・検索できるよう、タグを付与したい。それにより、「静か」「バリアフリー」「理解がある」などの特性で資源を絞り込める。

#### Acceptance Criteria
1. When ユーザーがタグを資源に付与するとき、the システムは Tag ノードを作成または既存ノードを利用し、HAS_TAG リレーションシップを作成すること
2. The システムは Tag に category プロパティ (atmosphere, accessibility, cost 等) を設定できること
3. When タグが使用されるとき、the システムは Tag.usage_count を自動的にインクリメントすること
4. The システムは 1つの資源に複数のタグを付与可能にすること
5. The システムは よく使われるタグをサジェスト機能で提示すること

### Requirement 3: エリアベース管理
**Objective:** 支援者として、資源を地理的エリアで管理・検索したい。それにより、利用者の居住地や活動範囲に合った資源を効率的に見つけられる。

#### Acceptance Criteria
1. When 資源を登録するとき、the システムは Area ノードを作成または既存ノードを利用し、LOCATED_IN リレーションシップを作成すること
2. The システムは Area に name, city, prefecture プロパティを保存すること
3. The システムは 1つの資源は 1つの Area にのみ所属させること
4. When エリアで検索するとき、the システムは そのエリア内の全資源を返すこと
5. The システムは 市区町村レベルのエリア粒度を標準とすること (例: 小倉北区、八幡東区)

### Requirement 4: 資源の検索・絞り込み
**Objective:** 支援者として、タグ、エリア、キーワードを組み合わせて資源を検索したい。それにより、利用者のニーズに合った場所・活動を効率的に発見できる。

#### Acceptance Criteria
1. When ユーザーがタグで検索するとき、the システムは HAS_TAG リレーションシップを辿って該当資源を返すこと
2. When ユーザーがエリアで検索するとき、the システムは LOCATED_IN リレーションシップを辿って該当資源を返すこと
3. When 複数のタグを指定するとき、the システムは AND 条件で絞り込むこと
4. When キーワードで検索するとき、the システムは name, description, address フィールドを対象に部分一致検索すること
5. The システムは 検索結果を feedback_count 降順でソート可能にすること
6. The システムは 検索結果を created_at 降順でソート可能にすること
7. When 検索結果がゼロのとき、the システムは 関連するタグや近隣エリアの提案を表示すること

### Requirement 5: フィードバック蓄積
**Objective:** 支援者として、実際に資源を使った経験をフィードバックとして記録したい。それにより、他の支援者が実際の使用感を判断材料にでき、情報が「生きた」ものに進化する。

#### Acceptance Criteria
1. When ユーザーがフィードバックを投稿するとき、the システムは Feedback ノードを作成し、content, visit_date, created_at を保存すること
2. When フィードバックが投稿されたとき、the システムは HAS_FEEDBACK リレーションシップで資源と紐付けること
3. When フィードバックが投稿されたとき、the システムは GIVEN_BY リレーションシップで投稿ユーザーと紐付けること
4. When フィードバックが追加されたとき、the システムは Resource.feedback_count を自動的にインクリメントすること
5. The システムは 1つの資源に複数のフィードバックを関連付け可能にすること
6. When フィードバックを表示するとき、the システムは 投稿者名、投稿日、訪問日を含めて表示すること
7. The システムは フィードバックに helpful_count プロパティを持たせ、役立った数を記録できること

### Requirement 6: 資源間のつながり管理
**Objective:** 支援者として、資源間の関係性（近接性、類似性、連続性）を記録したい。それにより、段階的支援ルート（例: 公園 → NPO → 作業場）を発見・共有できる。

#### Acceptance Criteria
1. When ユーザーが2つの資源の関係を登録するとき、the システムは RELATED_TO リレーションシップを作成すること
2. When つながりを作成するとき、the システムは relation_type (nearby, similar, sequential) を必須プロパティとして保存すること
3. The システムは distance, description プロパティを任意で保存できること (例: distance="徒歩5分", description="作業実習後に立ち寄れる")
4. When つながりが作成されたとき、the システムは created_by, created_at で情報源を記録すること
5. The システムは 1つの資源が複数の資源とつながりを持つことを許可すること
6. When 資源詳細を表示するとき、the システムは 直接つながっている資源を一覧表示すること

### Requirement 7: エゴネットワーク可視化
**Objective:** 支援者として、特定の資源を中心としたつながりネットワークを可視化したい。それにより、資源クラスターや段階的支援ルートを視覚的に把握できる。

#### Acceptance Criteria
1. When ユーザーが資源のエゴネットワークを要求するとき、the システムは その資源から1〜3段階のつながり (`[:RELATED_TO*1..3]`) を取得すること
2. The システムは エゴネットワークをグラフ構造 (ノード・エッジ) で返すこと
3. When ネットワークを描画するとき、the システムは relation_type に応じてエッジの色・スタイルを変えること
4. The システムは ネットワーク図にノード名、つながりの説明を表示すること
5. If 取得するつながりが100件を超える場合、the システムは 深さを制限し警告メッセージを表示すること

### Requirement 8: ニーズの記録
**Objective:** 支援者として、見つからない資源のニーズを記録したい。それにより、「探している人」の存在が可視化され、「知っている人」が情報を提供するきっかけになる。

#### Acceptance Criteria
1. When ユーザーがニーズを記録するとき、the システムは Need ノードを作成し、title, description, target, purpose, created_at を保存すること
2. When ニーズを記録するとき、the システムは IN_AREA リレーションシップで希望エリアと紐付けること
3. When ニーズを記録するとき、the システムは RECORDED_BY リレーションシップで記録ユーザーと紐付けること
4. The システムは Need.status を open, matched, closed のいずれかで管理すること
5. When ニーズが作成されたとき、the システムは status を open で初期化すること
6. The システムは ニーズに view_count を持たせ、閲覧数を記録すること
7. When ニーズ一覧を表示するとき、the システムは status="open" のニーズを優先的に表示すること

### Requirement 9: ニーズマッチング推薦
**Objective:** 支援者として、未マッチのニーズに対して候補資源を推薦してもらいたい。それにより、「探している人」と「知っている人」が自然に出会える。

#### Acceptance Criteria
1. When 未マッチのニーズが存在するとき、the システムは 同じエリア内の資源を候補として抽出すること
2. The システムは ニーズと候補資源のペアを match_quality (high, medium, low) 付きで返すこと
3. When ユーザーがマッチングを承認するとき、the システムは MATCHED_BY リレーションシップを作成すること
4. When マッチングが作成されたとき、the システムは matched_at, matched_by, note プロパティを記録すること
5. When マッチングが成立したとき、the システムは Need.status を matched に更新すること
6. The システムは 1つのニーズに複数の資源をマッチング可能にすること
7. When ニーズ記録者にマッチング通知を送るとき、the システムは 候補資源の詳細とマッチング理由を含めること

### Requirement 10: ユーザー管理・認証
**Objective:** システム利用者として、ユーザー登録・ログインを行い、自分の活動履歴を追跡可能にしたい。それにより、情報の信頼性が向上し、貢献度を可視化できる。

#### Acceptance Criteria
1. When ユーザーが新規登録するとき、the システムは User ノードを作成し、id, name, organization, created_at を保存すること
2. The システムは User.role に supporter, individual, family, resident のいずれかを設定すること
3. When ユーザーがログインするとき、the システムは セッションを確立し、ユーザーIDを保持すること
4. The システムは 資源登録時、フィードバック投稿時、ニーズ記録時に自動的にユーザーを紐付けること
5. When ユーザープロフィールを表示するとき、the システムは registered_resources 数と given_feedbacks 数を集計表示すること
6. The システムは ユーザーが自分の登録した資源・フィードバック・ニーズを一覧表示できること

### Requirement 11: データベースインデックス最適化
**Objective:** システムとして、頻繁に検索されるプロパティに対してインデックスを作成し、クエリパフォーマンスを最適化したい。

#### Acceptance Criteria
1. The システムは Resource.name, Resource.type にインデックスを作成すること
2. The システムは Tag.name にインデックスを作成すること
3. The システムは Need.status にインデックスを作成すること
4. The システムは Area.name にインデックスを作成すること
5. When データベースを初期化するとき、the システムは これらのインデックスを自動的に作成すること

### Requirement 12: 統計・分析機能
**Objective:** 運営者として、システムの利用状況と資源の蓄積状況を把握したい。それにより、地域で不足している資源を明確化し、コミュニティの成長を可視化できる。

#### Acceptance Criteria
1. The システムは 全資源数、全フィードバック数、全ニーズ数を集計できること
2. The システムは エリア別の資源分布を集計できること
3. The システムは よく検索されるタグ (Tag.usage_count 上位) を取得できること
4. The システムは ユーザー貢献度ランキング (登録資源数 + フィードバック数) を表示できること
5. When 統計データを取得するとき、the システムは 集計クエリを最適化し、5秒以内に結果を返すこと
6. The システムは 未マッチのニーズを分類し、不足資源タイプを明確化できること

## Non-Functional Requirements

### Performance
1. The システムは 検索クエリを3秒以内に返すこと (資源数1000件以下の場合)
2. The システムは エゴネットワーク取得を5秒以内に完了すること (深さ3、100ノード以下の場合)
3. The システムは 同時接続ユーザー数50名をサポートすること (Phase 1目標)

### Scalability
1. The システムは Phase 3 (Week 12-24) で資源数300件、フィードバック200件をサポートできること
2. When データ量が増加するとき、the システムは インデックスとクエリ最適化により性能劣化を最小化すること

### Usability
1. The システムは 検索結果ゼロの場合、ユーザーに代替候補を提示すること
2. The システムは フォーム入力でリアルタイムバリデーションを提供すること
3. The システムは グラフ可視化で直感的な操作 (ズーム、パン、ノードクリック) を提供すること

### Maintainability
1. The システムは Cypherクエリを集中管理し、再利用可能な構造にすること
2. The システムは データモデル変更時に既存データの移行スクリプトを提供すること
